## 功能描述

### 功能概述
IFU（Instruction Fetch Unit）是前端流水线中负责组织供指数据的重要模块，位于分支预测和指令缓存之后。在预测路径和 ICache 命中结果确定后，IFU 需要完成指令对齐、打包、简单的预译码等操作，并将处理好的指令送入后续模块（如 IBuffer）。

由于 IFU 处于供指链路的下游，其处理延迟将影响整个前端的取指响应能力，尤其在发生重定向（如分支预测错误）时，IFU 的执行周期会成为恢复路径的重要延迟点。因此，在功能完整和时序允许的前提下，尽量减少 IFU 的处理周期，有助于提升供指效率和预测失败恢复速度。

### 功能细化
- IFU 负责切分 ICache 传输的指令数据，确定预测块中每条指令的位置，并获得相应的有效指令数据。
- IFU 负责预译码，获取每条分支指令的分支类型及对应的 `jumpOffset`。从性能角度考虑，IFU 还会进行预译码检查，及早纠正可发现的预测错误。
- IFU 负责将 C 指令扩展为 32 位指令，并检查 C 指令是否合法。
- IFU 负责 MMIO/PBMT 取指，并阻止 MMIO 取指的推测执行。
- IFU 负责将 ICache 传递的异常信息与对应指令关联。
- IFU 需配合 IBuffer 入队，以减轻 IBuffer 的入队逻辑压力。
- IFU 支持同时对两个预测块进行指令位置定界、预译码和预译码检查，并同时向 IBuffer 入队。

### 设计考量
IFU 涉及多个模块的交互，需要权衡时序与成本。指令位置定界、IBuffer 入队以及从 ICache 读取 32 条指令均存在时序压力。大量指令并行处理和时序优化会增加面积与功耗；大量且紧耦合的数据处理也会增加物理设计中布局布线的压力，并可能劣化时序。随着前端供指量增大，IFU 的时序压力将显著上升。

## 总体设计

![IFU 的结构图](../figure/IFU/ifu-structure.svg)

### 主体结构的确定
IFU 与 FTQ、ICache、IBuffer 和 Uncache 总线交互：

1. IFU 接收 FTQ 的重定向信号，用于冲刷需置为无效的预测块，避免其传递至 IBuffer 后造成指令流错误。出于组合逻辑复杂度和时序考虑，设计避免对 IBuffer 进行精确到项级的冲刷。当 IFU 发现预译码结果与分支预测器给出的结果不符时，也会向 FTQ 发送重定向信号，及早纠正指令流。
2. IFU 完成预译码信息整理后，将有效指令数据传递给 IBuffer。
3. IFU 接收经 ICache 初步整理的取指信息。ICache 传递的 Data 由 SRAM 直出，当拍进一步加工的时序裕度较小，因此需寄存一拍后再处理。指令信息在 IFU 中经过两拍处理后送入 IBuffer。

在 V3 结构不变的前提下，IFU 最快需在 S1 阶段完成预译码，到 S2 阶段才能将整理后的指令数据传输给 IBuffer。目前预测检查位于 S2 阶段，会进一步缩减有效指令范围，以保障有效指令流。出于时序考虑，向 FTQ 传递的重定向信号延迟一拍：一是向 IBuffer 传递信息时仅需控制有效指令范围，逻辑复杂度相对较低；二是重定向需要计算目标地址，逻辑要求更高，且 IFU 发生重定向的频率较低，延迟一拍的影响可控。

### IFU 各级功能与时序预估
S0 级主要确定有效指令位置，并完成有效指令紧密排列所需的前置计算，是时序最紧张的部分。S1 级负责有效指令的紧密排列、与 IBuffer 接口交互所需的对齐操作，以及预译码。S2 级负责将 C 指令转换为 I 指令、判断指令是否合法，并检查预译码结果，及时纠正不符合预期的分支预测。S3 级计算 IFU 向 FTQ 发送的重定向地址。

需要注意的是，目前设计的想法主要在解决时序问题和功能实现上，对于面积和时钟门控没有过多考虑。计划在代码相对稳定后进行优化。

### 对 twoFetch 的配合
IFU 对 twoFetch 的处理理念是将两个预测块拼接为一个较大的预测块处理。V3 架构允许单个预测块最大为 64 字节；发生 twoFetch 时，两个预测块的大小之和也限制为 64 字节。该限制意味着每周期最少可向 IBuffer 入队 16 条、最多 32 条指令；更大的入队宽度会给 IBuffer 带来显著时序压力。若两个预测块的总取指宽度超过 64 字节，则需截断并分两拍处理。此外，两个预测块共用 64 字节的预译码逻辑可避免各自处理时所需的 128 字节预译码逻辑，降低实现开销。

IFU 主要配合 ICache 进行 twoFetch 处理，其处理逻辑受 ICache 传输数据格式影响。目前 ICache 传递与预测块对齐的 `maybeRvcMap` 信息及两行 `cacheLine` 数据，每行 `cacheLine` 数据对应一个预测块。这里的 `cacheLine` 并非 ICache 的原始 `cacheLine` 数据：预测块可能跨行，跨行时 ICache 会根据预测块实际可能使用的数据范围，将两行 `cacheLine` 数据融合为一行。

根据预测块的首地址和大小，可以通过索引抽取所需的指令数据。通过 `instrBoundary` 对指令进行定界后，可确定有效指令的位置；再根据预测块大小，判断合并后预测块的各部分分别使用预测块 1 或预测块 2 的数据。

为支持 twoFetch，IFU 还需处理保留一个预测块而舍弃另一个预测块，或同时舍弃两个预测块的情形。目前设计限制了 twoFetch 的产生条件：仅当 FTQ 中累积一定数量的预测块时才允许产生 twoFetch。该限制规避了高级分支预测器产生 `Override` 信号时对 twoFetch 情形的冲刷，简化了 IFU 的冲刷逻辑。

取指过程中，预测块末尾有时会出现半条指令。此时保留该半条指令，并由下一个预测块拼接处理。在 twoFetch 情况下，需要分别保留两个半字节，以便 IFU 自检发现预测结果不符合预期时，能够按需保留正确的半条指令。

### 有效指令排序
IFU通过compact函数完成有效指令的紧密排序。有效指令排序依赖前缀计数（Rank）实现。定义槽位 $i$ 的 $rank(i) = \sum_{k < i} valid(k)$；当满足 $valid(i) \land rank(i) = j$ 时，槽位 $i$ 对应第 $j$ 条有效指令。

为进一步降低多路选择器扇入，可将候选扫描窗口限定为[idx, 2·idx] (或保守取2·(idx+1))。该优化成立依赖两个前提：a. RISC‑V指令仅2或4字节，最优全RVC时当前指令在槽位idx，最差全4字节时在槽位2·idx；b. 有效指令之间不存在连续无效槽位。前提②保证了窗口内不会因异常空洞导致目标匹配缺失，使得窗口压缩在工程上安全且完备。所有指令属性受同一独热信号控制，确保原子绑定。

### 预译码
IFU通过getJalOffset、getBrOffset、BranchAttribute.decode函数对指令进行译码来获得相应的指令立即数Offset，以及CFI指令类型。

对于 C 指令，`RvcExpander.scala` 中的 RvcExpander 负责将其转换为 I 指令。模块还会检查 C 指令是否合法：若非法，则输出 C 指令的非法标记 `ill` 并保持原始数据；若合法，则输出转换后的 I 指令。

理论上，所有 C 指令均可转换为 I 指令。若时序允许，在前期完成转换可使后续模块仅处理 I 指令，从而降低处理复杂度。对于非法 C 指令，需保留异常原因，因此送入后续流程的是原始指令。
